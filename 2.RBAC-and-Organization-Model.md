# CoESCD Platform — RBAC and Organizational Governance Model

---

## 1. Executive Summary

The CoESCD platform operates inside a formal government hierarchy with strict chains of command, multi-party document approval workflows, sensitive data isolation requirements, and strict auditability obligations. A flat role-based access control system — the kind that ships with most web frameworks — is architecturally inadequate for this environment.

The recommended model is a **layered authorization architecture** that combines four distinct control mechanisms:

1. **Role-Based Access Control (RBAC)** for capability grants — what a user is allowed to do in the system
2. **Hierarchical Position Authority** for scope resolution — how far a user's authority extends across the organizational tree
3. **Resource Classification and Ownership Scoping** for data isolation — which specific records a user is permitted to touch
4. **Contextual Policy Rules** for workflow-specific decisions — time-bound delegation, acting assignments, emergency overrides, and approval chain enforcement

These four layers operate together at every authorization decision point. The Authorization domain evaluates all four and returns a single allow/deny decision. No domain implements its own access logic. No shortcuts exist.

The organizational model separates three conceptually distinct structures that are frequently conflated: the **administrative hierarchy** (who reports to whom), the **command chain** (who can direct whose work), and the **workflow authority chain** (who must approve what). These are related but not identical, and confusing them produces an access model that is either too permissive or too rigid to function in practice.

The entire model is designed to be SSO-ready, delegation-aware, classification-enforcing, and fully auditable from day one.

---

## 2. Access Control Design Principles

These principles are not aspirational. They are binding constraints on every design decision in this document. Any proposed design that violates a principle requires explicit justification and documented trade-off acceptance.

### P1 — Least Privilege by Default

No user receives any permission they did not explicitly need for their defined role and position. New accounts have zero capabilities until roles are assigned. Broad permissions are never granted to simplify administration. When in doubt, deny.

### P2 — Explicit Over Implicit

Access is granted explicitly, never assumed from membership or proximity. Being in a department does not automatically grant access to that department's documents. Holding a senior position does not automatically grant access to every subordinate's data. Every grant must be traceable to a role, a scope assignment, a delegation record, or a classification clearance.

### P3 — Separation of Concern Between Capability and Scope

A user's **capability** (what actions they can perform) is separate from their **scope** (which records those actions apply to). A department analyst has the capability to create reports — their scope determines which department's data they can report on. This separation prevents the common mistake of solving scope problems with role proliferation.

### P4 — Single Authoritative Decision Point

All authorization decisions flow through one service. No domain evaluates permissions itself. No domain stores its own copy of the permission model. This is not a convenience — it is a security requirement. Distributed permission evaluation creates inconsistency, makes auditing unreliable, and makes security policy changes incomplete.

### P5 — Positions Are First-Class Entities

Workflow authority — task assignment, document approval, correspondence routing — belongs to organizational **positions**, not to individual users. A user exercises authority because they occupy a position. When a user leaves a position, the authority leaves with them. This is how government institutions actually operate and the model must reflect it.

### P6 — Classification Is a Hard Constraint

A resource's confidentiality classification is a ceiling, not a preference. A user without the required clearance level cannot access a classified resource regardless of their role, their position, or any other factor — unless an explicitly authorized override exists, which itself is logged and auditable.

### P7 — All Privilege Is Auditable

Every privilege grant, role assignment, delegation creation, access decision for sensitive resources, and administrative configuration change must produce an immutable audit record. "We can check who did this" must always be true.

### P8 — Delegation Is Bounded and Time-Limited

Authority can be delegated within defined limits. Delegation does not transfer ownership of authority — it grants a temporary, scoped, revocable copy. A delegate cannot re-delegate. Delegation expires. Expired delegations produce no access.

### P9 — Administrative Authority Is Segmented

No single administrator role grants all-encompassing access. User management, permission management, security configuration, infrastructure configuration, and audit access are separate administrative domains with separate roles. No one should be able to simultaneously create a user, assign that user a sensitive role, and delete the audit trail of those actions.

### P10 — The Model Must Be Explainable

Any access decision — allow or deny — must be explainable in terms the platform administrator can understand and verify: "User X was allowed to approve Document Y because they hold Position Z, which has role R, which grants permission P, and Document Y's classification C is within their clearance level L." An opaque authorization model is a security liability.

## 3. Recommended Authorization Model

### 3.1 Why Pure RBAC Is Insufficient

Standard RBAC assigns roles to users and permissions to roles. It answers the question: "Does a user with role R have permission P?" This is necessary but insufficient for CoESCD because:

- It has no concept of organizational scope. "Department Head" and "Department Head of the Fire Safety Department" are different things — RBAC alone cannot express the latter without role explosion.
- It cannot express hierarchical authority inheritance. The fact that a Deputy Chairman inherits certain access rights from the departments below them is not a role assignment — it is a structural property.
- It cannot express resource classification constraints. A document at "Confidential" level is inaccessible to users below "Confidential" clearance regardless of role.
- It cannot express time-bound or context-bound conditions like delegations, acting assignments, or emergency overrides.

Expanding RBAC alone to cover these cases results in thousands of roles, many nearly identical, maintained by administrators who cannot reason about the system. This is a common failure mode in enterprise IAM systems.

### 3.2 The Recommended Layered Model

The authorization model is composed of four layers that are evaluated in sequence for every access decision:

---

**Layer 1 — Capability Layer (RBAC)**

Answers: "Is this user capable of performing this action type at all?"

A user is assigned one or more roles. Each role grants a set of fine-grained capability permissions. These are action-type capabilities, not resource-specific grants. Examples:

- `document.create`
- `document.approve`
- `document.view`
- `task.assign`
- `task.complete`
- `gis.layer.edit`
- `analytics.report.generate`
- `admin.user.create`
- `audit.log.view`

If the user's combined roles do not include the required capability, the decision is **deny** immediately. No further evaluation needed.

This layer is evaluated purely from role-permission assignments. It is fast, cacheable, and static between role changes.

---

**Layer 2 — Scope Layer (Positional Hierarchy Authority)**

Answers: "Does this user's organizational authority extend to the target resource's owner?"

If Layer 1 passes, the system evaluates whether the resource falls within the user's authority scope. This is derived from the user's current position in the organizational hierarchy and the ownership of the resource.

Scope types evaluated at this layer:

- **Own scope:** the resource belongs to the user directly (they created it, or it was assigned to them)
- **Department scope:** the resource belongs to the user's department
- **Subordinate scope:** the resource belongs to a department or position that sits below the user's position in the hierarchy
- **Organization-wide scope:** the resource is visible to all authorized users regardless of department
- **Explicit grant scope:** the resource has been explicitly shared with this user or their position

If the resource falls outside the user's scope and no explicit grant exists, the decision is **deny**. A Department Head cannot access another department's documents even if their role technically grants `document.view`.

This layer is evaluated dynamically using the live organizational hierarchy. It is cached with invalidation on org structure changes.

---

**Layer 3 — Classification Layer (Confidentiality Constraint)**

Answers: "Does this user's clearance level meet the resource's classification requirement?"

If Layers 1 and 2 pass, the resource's classification level is compared against the user's clearance level. Classification levels are ordered:

`Unrestricted < Internal < Department-Confidential < Restricted < Confidential < Secret`

A user's clearance level is a property of their position (and can be explicitly elevated by a security administrator for specific users). Access is permitted only when the user's clearance level is greater than or equal to the resource's classification.

This layer has no exceptions driven by role or scope — it is a hard constraint. The only override is an explicit emergency access grant, which itself requires elevated authority and produces an audit event.

---

**Layer 4 — Policy Layer (Contextual Rules)**

Answers: "Do any active contextual policies modify this decision?"

This layer evaluates dynamic conditions that override or supplement the previous layers:

- **Delegation grants:** User B has been delegated authority by User A for a defined scope and time window. This may expand User B's effective scope for the delegation period.
- **Acting assignment:** User B is currently acting in Position X, which carries Position X's authority scope.
- **Workflow state constraints:** A document in "Under Approval" state can only be acted upon by the current designated approver, even if other users have `document.approve` capability.
- **Time-bound restrictions:** Some roles or grants are active only during defined time windows.
- **Emergency access grants:** A specifically authorized, fully logged temporary elevation for emergency operational conditions.

This layer applies after all other layers and can expand (delegation, acting) or further restrict (workflow state) access.

---

**Final decision:** Allow only if all four layers produce a compatible allow signal. Any deny in any layer produces a final deny, with the denying layer recorded in the audit event.

### 3.3 ABAC Clarification

This model is sometimes called "RBAC + ABAC hybrid." That framing is partially accurate but imprecise. The model does not implement a general-purpose ABAC policy engine with arbitrary attribute combinations — that would be over-engineered and difficult to reason about for administrators. Instead, the contextual rules in Layer 4 are a specific, bounded set of policy types that are well-understood and explicitly configured. The model is deterministic and explainable, not a general policy language.

## 4. Organizational Hierarchy Model

### 4.1 Conceptual Entities

The organization is modeled through six distinct conceptual entity types. Understanding their distinctions is essential for building a correct access model.

---

**Organization Root**

The single root node of the entire organizational tree. In CoESCD's case, this is the Committee itself as a legal and administrative entity. The Organization Root is the parent of all top-level organizational units. It is the boundary of the platform — all users, departments, and positions exist within it. Cross-organization federation (e.g., collaboration with other government agencies) is handled through explicit inter-organizational grants, not by placing external entities inside this root.

---

**Leadership Domain**

A special organizational construct for senior officials whose authority spans the entire organization but who may not fit neatly into a single branch of the department tree. The Chairman, Deputy Chairmen, and Chief of Staff exist in this domain.

The Leadership Domain is not a department — it does not own operational documents in the same way departments do. It is a structural zone that defines the top of the command chain from which authority flows downward into the department tree.

Why model this separately: If the Chairman is simply placed inside one department, then the organizational hierarchy computation assigns them authority only over that branch. Their actual authority spans all branches. Modeling them in the Leadership Domain with a defined authority scope of "organization-wide" resolves this cleanly without special-casing every permission check.

---

**Organizational Unit (Department)**

A formal administrative or operational division of the organization. Departments are the primary ownership boundary for resources — documents, tasks, files, and GIS layers are owned by a department (more precisely, by a position within a department, but the department is the aggregation boundary).

Departments form a tree structure. A department can have sub-departments, units, and sections as children. The tree depth is not artificially limited, but in practice government organizations rarely exceed four or five levels of nesting below the root.

Key properties of a Department:
- Has a unique identifier and formal name
- Belongs to one parent (except top-level departments, which belong to the Organization Root)
- Has one designated Head position
- Has an ordered list of member positions
- Has a defined confidentiality scope (what classification levels are handled here)
- Maintains a history of structural changes (departments that were merged, split, renamed)

---

**Position**

The fundamental unit of organizational authority. A Position is a formally defined slot in the organizational hierarchy — it exists independently of who occupies it.

Examples: "Head of the Fire Safety Department," "Deputy Chairman for Operations," "Senior Analyst, Seismic Monitoring Unit."

Key properties of a Position:
- Has a unique identifier and formal title
- Belongs to exactly one Organizational Unit (or the Leadership Domain)
- Has a defined rank/grade within the organization
- Has a defined authority scope (what units are under this position's command)
- Has a defined clearance level
- Has defined roles that are automatically associated with this position (positional roles)
- Has a defined reporting-to relationship (which position this position reports to)
- Maintains occupancy history (who held this position when)
- Can be vacant (no current occupant)

The separation between Position and User is non-negotiable. Workflows route to positions. When a position is vacant, the workflow pauses or escalates to the reporting line — it does not fail silently.

---

**Position Occupancy**

The link between a User and a Position at a specific point in time. An Occupancy record has:
- The position
- The user occupying it
- Start date
- End date (null if current)
- Occupancy type: Primary, Acting, Temporary

A user can have multiple concurrent occupancies (e.g., a department head also acting as Deputy Chairman during a deputy's absence). Each occupancy activates the roles and authority scope of the corresponding position for that user, for the duration of the occupancy.

---

**Reporting Relationship**

An explicit record of which position reports to which other position. This is the backbone of the command chain and the basis for hierarchical scope computation.

Reporting relationships are directional: Position A reports to Position B. This means: Position B has authority over Position A's work. Position B can assign tasks to Position A. Position B is in Position A's approval escalation chain.

Reporting relationships are stored as explicit records, not inferred solely from the department tree. This is important because some positions may have reporting lines that cross department boundaries — a specialist who is administratively in Department X but operationally reports to a Deputy Chairman for a specific function.

---

### 4.2 Structural Rules

- Every position (except the top of the Leadership Domain) has exactly one reporting-to relationship.
- The reporting graph must be acyclic — no circular reporting chains.
- Reporting relationships are versioned — changes produce historical records, not overwrites.
- A position with no occupant is valid. Workflows routed to a vacant position escalate to the reporting-to position.
- The department tree and the reporting relationship graph are related but distinct. The department tree defines administrative ownership. The reporting graph defines command authority.

---

### 4.3 Functional vs. Administrative Hierarchy

A user may have an **administrative home** (the department they formally belong to for HR and administrative purposes) and a **functional reporting line** (who they actually answer to for specific work). In some government contexts these coincide; in others they do not.

The model supports this by:
- Primary position occupancy defines the administrative home
- Reporting relationships define functional command chains
- Where these differ, both are represented and the authorization model uses the functional reporting relationship for workflow authority decisions

---

## 5. Position, Reporting Line, and Command Chain Model

### 5.1 The Three Authority Hierarchies

Three distinct authority structures exist within CoESCD. They overlap but are not identical. Conflating them produces incorrect access decisions.

---

**Administrative Hierarchy**

Defines organizational membership, resource ownership, and administrative responsibility. The department tree is the administrative hierarchy. It determines:
- Which department owns a document, task, or file
- Which department head is responsible for a unit's operations
- How administrative reports and statistics are aggregated

Administrative hierarchy does not automatically grant command authority over other departments' work.

---

**Command Chain**

Defines who can direct whose operational work. The command chain is the reporting relationship graph. It determines:
- Who can assign tasks to whom
- Who receives escalations when a task is overdue
- Who can access a subordinate's work for supervisory purposes
- Whose approval is required before work proceeds

The command chain follows reporting relationships. A Deputy Chairman in the command chain has authority over all positions that report (directly or transitively) to them, regardless of which department those positions belong to.

---

**Workflow Authority Chain**

Defines who must participate in a specific workflow — document approval, budget authorization, operational order issuance. The workflow authority chain is defined per document type or workflow type and references positions, not individual users.

Example: An incident report of type "Major Emergency" requires approval from: (1) the submitting analyst's department head, (2) the relevant Deputy Chairman, (3) the Chairman. This chain is a configuration of the workflow engine, not a fixed property of the organizational hierarchy.

Workflow authority chains can reference positions by role within the hierarchy (e.g., "the department head of the submitting user's department") or by explicit position (e.g., "the Chairman"). This flexibility is necessary because approval requirements vary by document type and operational context.

---

### 5.2 Command Chain Computation

For any user, the system must be able to answer:
- "Which users are this user's direct reports (one level down)?"
- "Which users are this user's transitive subordinates (all levels down)?"
- "Who is this user's direct superior?"
- "Who is this user's chain of command upward to the organization root?"

These are graph traversal operations over the reporting relationship graph. The results are cached and invalidated on organizational structure changes.

The computation uses position occupancies as the anchor — a user's command chain authority is the union of command chains for all positions they currently occupy.

---

### 5.3 Task Assignment Authority Rules

Task assignment follows the command chain. The rules are:

- A user may assign tasks to any position in their transitive subordinate set
- A user may assign tasks to themselves
- A user may not assign tasks to peers, superiors, or positions outside their command authority — unless a cross-department delegation exists
- A user may reassign a task they own (were assigned as assignee) to a subordinate, creating a sub-task delegation chain
- Sub-task delegation does not transfer ownership of the original task — the original assignee remains accountable

These rules are enforced by the Authorization domain at task creation and reassignment time. They are not advisory warnings.

---

### 5.4 Document Approval Chain Resolution

When a document enters an approval workflow, the system resolves the approval chain dynamically:

1. Identify the document's type and classification
2. Look up the workflow configuration for that document type
3. Resolve each step in the configuration to a current position occupant
4. If a step's position is vacant, apply the vacancy rule: escalate to the reporting-to position

Approval chain resolution produces an ordered list of current users (by position) who must approve, in sequence. This list is computed at workflow initiation and stored as the active approval chain for that document instance. If the org structure changes mid-workflow, the stored chain governs — it is not re-computed mid-approval unless an administrator explicitly resets the workflow.

## 6. Role Model

### 6.1 Role Taxonomy

Roles exist at multiple levels. Understanding the distinction between role types is essential for avoiding role explosion and maintaining a manageable permission model.

---

**Positional Roles (Computed, Not Assigned)**

These roles are automatically active for a user because of the position they currently occupy. They are not assigned by an administrator — they are derived from position occupancy.

When a user is assigned to a position (primary, acting, or temporary), the roles defined for that position become active for them. When they leave the position, those roles are deactivated.

Positional roles define the baseline capability of every position in the organization. They are defined at position creation by the organizational administrator and reviewed during position restructuring.

Examples:
- "Department Head" position → activates `dept_head_role` (can approve department documents, assign tasks within department, view department analytics)
- "Senior Analyst" position → activates `senior_analyst_role` (can create analytical reports, edit GIS layers within department, view incident data)
- "Clerk" position → activates `clerk_role` (can create and route documents, manage document correspondence)

The assignment of roles to positions is a security-significant configuration change and is audit-logged.

---

**Functional Roles (Manually Assigned)**

Capabilities that a specific user needs beyond what their positional role provides, assigned explicitly by an authorized administrator.

Functional roles are used when a user has responsibilities that cross the boundary of their formal position. Examples:
- An analyst who also coordinates inter-department data exchange gets the `data_exchange_coordinator` functional role
- A department clerk who also manages document archiving gets the `archive_manager` functional role

Functional roles must be justified, scoped, and reviewed periodically. They must not be used to work around the positional role model — if everyone in a position needs a capability, it belongs in the positional role, not as a functional role on each user.

---

**Administrative Roles (Separately Governed)**

Roles that grant capabilities in the administration and governance layer. These are strictly separated from operational roles and follow the separation-of-duties model defined in Section 8.

Administrative roles include:
- `platform_admin` — manages system configuration, integrations, feature flags (no access to business data)
- `user_admin` — creates, modifies, and deactivates user accounts (no access to permission assignments or security settings)
- `org_admin` — manages departments, positions, and reporting lines (no access to individual user permissions)
- `role_admin` — assigns roles to positions and functional roles to users (no access to security configuration)
- `security_admin` — manages clearance levels, classification policies, audit access (no access to user creation or business data)
- `audit_viewer` — read-only access to audit logs (no operational access)

These are not combinable in a single user account without explicit security review and documented justification.

---

**Module-Specific Roles**

Roles that grant access within a specific functional module, used when the default positional role is insufficient or too broad. These are governed by the module's functional domain.

Examples:
- `gis_layer_editor` — can create and modify GIS layers (beyond the default analyst view)
- `conference_moderator` — can manage and record organizational conferences
- `analytics_publisher` — can publish analytical reports to organization-wide visibility

---

**Temporary Roles**

Roles that are assigned with an explicit expiry date and time. Used for delegation and time-limited special access. A temporary role that has passed its expiry date produces no access, even if not explicitly revoked. The system must enforce expiry enforcement actively — not reactively.

---

### 6.2 Role Hierarchy and Inheritance

Role inheritance is limited and explicit. A role can declare that it inherits all permissions of another role. This is used sparingly — only where the inheritance relationship is a genuine organizational reality (a "Senior Department Head" role legitimately inherits all permissions of "Department Head").

Role inheritance is never implied or structural. Being above someone in the org chart does not mean inheriting their role's permissions. Hierarchical authority over a subordinate's scope (the scope layer) is separate from inheriting their role's capabilities.

This distinction prevents privilege escalation through the org chart — a Deputy Chairman does not automatically acquire all the detailed operational permissions of every analyst beneath them. They have supervisory scope, not identical capability.

---

### 6.3 What Should Be Static vs. Dynamic

**Static (defined at configuration time, rarely changed):**
- The set of permissions associated with each role
- The set of roles associated with each position
- The permission definitions themselves

**Dynamic (changes frequently, driven by HR and administrative operations):**
- Which user occupies which position
- Which functional roles are assigned to which users
- Whether a delegation is currently active
- Whether a temporary role has expired

The distinction matters for caching: static data is aggressively cached with manual invalidation. Dynamic data is cached with short TTL or event-based invalidation.

## 7. Permission and Scope Model

### 7.1 Permission Structure

Permissions are the atomic units of capability. They are defined at platform design time, not by administrators at runtime. Administrators assign roles; developers define what permissions those roles include.

A permission is expressed as: `[resource_type].[action].[optional_qualifier]`

**Resource types** correspond to platform domain objects:
`document`, `task`, `file`, `message`, `channel`, `call`, `conference`, `gis_layer`, `incident`, `report`, `user`, `department`, `position`, `role`, `audit_log`, `system_config`

**Actions** are standardized verbs:
`create`, `view`, `edit`, `delete`, `approve`, `reject`, `assign`, `route`, `export`, `import`, `publish`, `archive`, `restore`, `configure`, `grant`, `revoke`

**Optional qualifiers** narrow the permission further:
`own` (only records owned by the user), `department` (records owned by the user's department), `subordinate` (records owned by positions in the user's subordinate scope), `any` (no scope restriction — used for administrative and supervisory roles)

**Examples of fully expressed permissions:**
- `document.view.department` — view documents owned by the user's department
- `document.approve.subordinate` — approve documents submitted by subordinate positions
- `task.assign.subordinate` — assign tasks to positions within the user's command chain
- `gis_layer.edit.own` — edit GIS layers created by the user
- `audit_log.view.any` — view all audit records (audit viewer role only)
- `user.create.any` — create user accounts (user admin role only)
- `role.grant.department` — assign roles to users within the user's department (department-scoped role admin)

### 7.2 Scope Dimensions

Scope defines the set of records to which a capability permission applies. Scope is evaluated at the resource level during access decisions.

**Own Scope**
The user is the creator or the designated individual owner of the resource. This is the narrowest scope. Any user with a `view.own` permission can see their own records.

**Department Scope**
The resource is owned by a position within the user's primary department. Department scope is bounded — it does not extend to sub-departments unless explicitly configured as "including subordinate units."

**Subordinate Department Scope**
The resource is owned by a position within any department that falls below the user's position in the command chain hierarchy. This is the supervisory scope. A department head sees their unit's records plus subordinate units' records.

**Organizational Scope**
The resource is accessible to any authenticated user with the appropriate capability and clearance. Used for organization-wide announcements, shared reference documents, and public-internal resources.

**Explicit Grant Scope**
The resource has been explicitly shared with this specific user, position, or department by an authorized party. Explicit grants extend access beyond the natural scope boundaries. They are recorded as separate access grant records, are revocable, and are audit-logged.

**Classification-Bounded Scope**
Regardless of other scope computations, a resource at classification level C is visible only to users with clearance level ≥ C. Classification scope is a filter applied after all other scope calculations.

---

### 7.3 Permission Evaluation Algorithm

When the Authorization domain receives a request `can(userId, action, resourceType, resourceId)`, it executes this evaluation:

**Step 1 — Capability check:**
Collect the user's current active roles (positional roles from all current occupancies + assigned functional roles + active temporary roles). Compute the union of all permissions from those roles. Check whether `[resourceType].[action].*` appears in the union. If not, return deny with reason `CAPABILITY_NOT_GRANTED`.

**Step 2 — Scope check:**
If resourceId is provided, determine the resource's owner (the position and department that created/owns it). Determine whether this owner falls within the user's authority scope (own, department, subordinate, organization-wide, or explicit grant). If not, return deny with reason `RESOURCE_OUT_OF_SCOPE`.

**Step 3 — Classification check:**
Retrieve the resource's classification level. Retrieve the user's effective clearance level (from their highest-ranking current position, or an explicitly elevated clearance if set by security admin). If classification > clearance, return deny with reason `CLASSIFICATION_EXCEEDS_CLEARANCE`.

**Step 4 — Policy check:**
Evaluate active contextual policies: Is there an active delegation that grants additional scope? Is there a workflow state constraint that restricts who can act on this specific resource right now? Is there a time-bound restriction active? Apply any modifiers and produce the final decision.

**Return:** allow (with the evaluated effective scope) or deny (with the specific reason and the layer that denied).

All results are cached keyed on (userId, action, resourceType, resourceId) with a short TTL. Cache is invalidated on: role assignment changes, org structure changes, resource classification changes, delegation state changes.

## 8. Delegation and Temporary Authority Model

### 8.1 Delegation Principles

Delegation is the controlled transfer of a subset of a user's authority to another user for a bounded time and scope. It is not a backdoor — it is a formally governed operation that is fully auditable and subject to the same constraints as permanent authority.

---

### 8.2 What Can Be Delegated

The following authority types support delegation:

**Task assignment authority:** Position A delegates to Position B the authority to assign tasks on behalf of Position A, within a specific scope (e.g., within a specific project, or for a specific set of subordinate positions), for a specific time window.

**Document approval authority:** Position A delegates approval authority for a specific document type or classification level to Position B, for a specific time window. The approval action taken by Position B is recorded as "Approved by [B] on behalf of [A] by delegation [reference]."

**Document routing and signing authority:** Position A delegates the authority to route or sign outgoing correspondence to Position B.

**Department head authority (Acting Assignment):** When a department head is absent, their authority (as defined by their position's role set and scope) is transferred to an acting head. This is a full positional authority delegation — the most comprehensive type and the most tightly controlled.

**Module access expansion:** A user delegates access to their own resources in a specific module to another user (e.g., a supervisor delegates access to their task board to a coordinator for monitoring purposes).

---

### 8.3 What Must Never Be Delegated

The following cannot be delegated under any circumstance:

**Administrative authority over user accounts and roles.** A `user_admin` or `role_admin` cannot delegate their administrative capabilities to an operational user. Administrative capabilities are position-bound, not delegable.

**Security configuration authority.** A `security_admin`'s authority over classification policies, clearance assignments, and audit access cannot be delegated.

**Audit log access.** An `audit_viewer`'s ability to view audit records cannot be delegated to a non-auditor.

**Clearance levels.** A user's security clearance is their own. They cannot delegate clearance to access classified resources on behalf of someone with lower clearance. A delegate acting under a delegation grant operates with the intersection of their own clearance and the delegating user's scope — never an elevation of their own clearance.

This last point is critical: **delegation is scope expansion, never clearance elevation.** If User B has Clearance Level 2 and User A (Clearance Level 4) delegates task approval authority to User B, User B can approve tasks within that delegation scope — but only tasks at Classification Level ≤ 2. They cannot approve classified tasks on behalf of User A.

---

### 8.4 Delegation Record Model

A delegation is a formal record containing:

- **Delegator:** the user granting authority (must currently hold the authority being delegated)
- **Delegate:** the user receiving the authority
- **Authority type:** what specific authority is being delegated (mapped to a bounded set of permission types)
- **Scope:** the resource scope within which the delegation applies (own department, specific project, specific document type, etc.)
- **Start date and time**
- **End date and time** (mandatory — open-ended delegations are not permitted)
- **Reason/justification** (mandatory — recorded as text, typically referencing a leave approval or operational order)
- **Authorization reference:** the record of who authorized this delegation (in most cases the delegator themselves; for acting department head assignments, an administrator or superior must counter-authorize)
- **Status:** active, expired, revoked
- **Revocation record** (if applicable): who revoked it, when, and why

---

### 8.5 Acting Assignment

Acting assignments are a special category of delegation where a user fully assumes the positional authority of another position. This is used when:
- A department head is on extended leave
- A Deputy Chairman position is temporarily vacant
- A position holder is temporarily performing duties for a higher position

An acting assignment:
- Creates a temporary Position Occupancy record of type "Acting"
- The acting user's effective roles and scope include the full positional role set of the position they are acting in
- The acting period is bounded by explicit dates
- Must be authorized by a superior position (not self-authorizing)
- Cannot be re-delegated by the acting user
- Is prominently recorded in all actions taken during the acting period: "Approved by [User] acting as [Position]"

When the original position holder returns, the acting assignment is closed. The original occupancy record remains unchanged — there is no conflict because positional authority is computed from occupancy records, and the acting record has its own bounded time window.

---

### 8.6 Revocation Behavior

Delegation revocation is immediate. When a delegation is revoked:
- The delegation record's status is set to `revoked` with timestamp, revoker identity, and reason
- The Authorization domain's cache for the delegate is invalidated immediately
- Any in-progress workflows that were authorized under this delegation are flagged for review — they are not automatically rolled back, but an administrator alert is raised

A delegation expiring naturally (reaching its end date) is equivalent to revocation but does not raise an alert. Expiry is expected. Revocation before expiry is potentially significant and is logged as a noteworthy event.

## 9. Separation of Duties Model

### 9.1 Principle

Separation of duties (SoD) is a control that ensures no single user can complete a sensitive end-to-end operation alone. In a government platform, SoD protects against both external abuse and internal fraud or error.

---

### 9.2 Administrative SoD Boundaries

The following administrative capability pairs must never be held by the same user simultaneously:

**User creation + Role assignment:**
A `user_admin` who can create accounts must not also be a `role_admin` who can assign sensitive roles. If a single person could do both, they could create an account and immediately grant it administrative permissions with no second-party oversight.

**Role definition + Role assignment:**
A user who defines what permissions a role contains must not also be able to assign that role to users. This separation ensures that expanding a role's permissions requires explicit action by a role definer, and a separate action by a role assigner — providing a two-party check.

**Security configuration + User administration:**
A `security_admin` who configures clearance levels and classification policies must not also be a `user_admin` who creates accounts. This prevents a single actor from both lowering classification requirements and creating accounts that exploit the lowered requirements.

**Operational administration + Audit access:**
A `platform_admin` with operational access must not also hold `audit_viewer` privileges in a mode that allows modifying audit retention policies. This prevents an admin from both taking an action and controlling whether that action's record persists.

**Document initiator + Final approver:**
Within the EDMS, the user who initiates a document or submits it for approval cannot be the final approver of that same document. Multi-party approval workflows must include at least one approver who is not the submitter. This is enforced at the workflow engine level, not just by role convention.

---

### 9.3 Operational SoD Boundaries

**Task assignment + Execution completion verification:**
A supervisor who assigns a task should not be the same person who marks it complete without review. For significant operational tasks, completion must be verified by the assigning authority or a designated reviewer.

**Incident report creation + Official publication:**
A field analyst who creates an incident report cannot publish it as an official organizational record without approval from a designated reviewer (typically their department head or a designated analytical supervisor).

**GIS layer creation + Layer promotion to operational use:**
Creating a GIS hazard layer and promoting it to the operational map view must be separate actions authorized by separate roles. An analyst can create and test layers; a GIS administrator or supervisor promotes them to operational status.

---

### 9.4 Enforcement Model

SoD constraints are enforced in two ways:

**Preventive enforcement:** The role assignment system checks SoD rules before completing a role assignment. If assigning Role B to User X would create an SoD violation (because User X already holds Role A), the assignment is rejected with an explanation. This is the primary enforcement mechanism.

**Detective enforcement:** A periodic SoD audit runs against the current role assignment database and reports any violations (which may have been introduced through legacy data, migration, or administrative error). Violations in the detective report must be resolved within a defined SLA.

SoD rules are defined in a configuration maintained by the `security_admin`. Adding or removing SoD rules is itself an audit-logged event.

## 10. Module-Specific Access Model

### 10.1 Electronic Document Management System (EDMS)

The access dimensions that matter in the EDMS are: document type, document state, document classification, ownership (which position created it), and routing (which positions are in the active approval chain).

**Visibility:** A document is visible to: (a) its creator, (b) any position in its current or historical approval chain, (c) users with department or subordinate scope who have `document.view.department` or `document.view.subordinate`, (d) explicitly granted recipients (for shared outgoing correspondence).

**State-based access:** A document in "Draft" state is visible only to its creator and direct supervisor. A document in "Under Approval" state is visible to the current approver, the prior approvers, and the creator. A document in "Signed/Final" state is visible per classification rules and scope. State-based visibility rules are enforced by the EDMS module's query layer, informed by the authorization decision.

**Approval action:** The capability `document.approve` is only exercisable by the user currently designated as the active approver in the document's approval chain. Even if another user holds the `document.approve` capability and has supervisory scope, they cannot approve a document that is not routed to their position. Approval is workflow-position-bound, not just role-based.

**Document number assignment:** Document numbers (official registry numbers) are assigned only by users with `document.number.assign` capability, typically clerks in the correspondence office. Numbering is a controlled action separate from content authorship.

---

### 10.2 Task Management

The access dimensions that matter in Task Management are: task ownership, task assignment chain, task classification, and task state.

**Visibility:** A task is visible to: (a) the assigner, (b) the assignee, (c) any supervisory user who has the assignee in their subordinate scope, (d) explicitly added observers.

**Assignment authority:** Enforced by the command chain model — `task.assign` is only executable for positions within the user's subordinate authority. The system validates this at assignment time and rejects out-of-chain assignments.

**Reassignment/delegation:** An assignee can create sub-tasks delegating work to their own subordinates. The parent task remains assigned to them — the sub-task is a child record. The original assigner retains visibility and can intervene.

**Escalation:** An overdue task triggers escalation upward through the reporting chain. Escalation does not transfer task ownership — it notifies the supervisor and grants them viewing access. Taking action on an escalated task requires the supervisor's explicit assumption of the task (logged as an override event).

---

### 10.3 File Management

The access dimensions that matter in File Management are: file classification, folder ownership, explicit shares, and linked-resource context.

**Folder hierarchy:** Folders have owners (a position and department). Access to a folder inherits the owning department's scope rules. A user with `department` scope can access their department's folders. Subordinate scope extends to subordinate department folders.

**File-level permissions:** Individual files can have access controls that override the folder's inherited rules — either more restrictive (a confidential file in an otherwise open folder) or more permissive (a file explicitly shared outside the department). Both overrides are explicit grant records, not implicit.

**Linked-resource context:** Files attached to tasks, documents, or messages inherit the visibility context of the host resource. If a task is visible to a user, its attached files are visible. If the task is reassigned, the file's visibility follows the task's new access context.

**Download vs. view:** Viewing a file (rendering in-browser) and downloading it (taking a local copy) are separate capabilities. For classified documents, download capability may be restricted even when viewing is permitted.

---

### 10.4 Chat and Messaging

The access dimensions that matter in Chat are: channel type, channel membership, and message classification.

**Direct messages:** Visible only to the two participants. No supervisory override for direct messages — this is intentional for operational trust. However, the existence of a direct message conversation (metadata: who communicated with whom, when) is retained in audit records for authorized security investigations.

**Department channels:** Visible to all users with an active position in the channel's owning department. Joining and leaving are automatic based on position occupancy — no manual channel management required for standard department channels.

**Cross-department channels:** Visible only to explicitly added members. Cross-department channel creation requires `channel.create.cross_department` capability (available to department heads and above).

**Task/document-linked channels:** A discussion thread linked to a specific task or document is visible to all users who have access to that task or document. Access is derived — it does not need to be managed independently.

**Retention and archival:** Messages in department channels and linked channels are retained per a configurable policy. Direct messages follow a separate retention policy. Security investigations with appropriate authorization can access retained messages.

---

### 10.5 Audio/Video Conferencing

The access dimensions that matter in Conferencing are: meeting type, participant list, and recording access.

**Scheduled meetings:** Created by users with `conference.create` capability. Participant invitations go to specific users or to positions. A user occupying an invited position receives the invitation.

**Ad-hoc calls:** Any user can initiate a direct call to another user they have messaging access to.

**Recording:** Recording a meeting requires explicit `conference.record` capability and produces an audit event. Recorded meetings are stored with the classification level of the most sensitive topic discussed — this is set by the meeting organizer at creation and can be elevated during the meeting by a participant with sufficient authority.

**Recording access:** Only invited participants and users with explicit grants can access recordings. The conference organizer can control who has post-meeting access. Classification rules apply.

---

### 10.6 GIS and Maps

The access dimensions that matter in GIS are: layer type, layer classification, and operational vs. draft state.

**Base map layers:** Viewable by all authenticated users with `gis.view` capability. Base maps contain no sensitive information.

**Operational layers (hazard zones, incident locations):** Viewable by users with `gis.layer.view` capability and appropriate classification clearance. These layers may contain sensitive emergency assessment data.

**Draft/analysis layers:** Created by analysts, visible only to the creator and their department by default. Promoted to operational status by a `gis_admin` or department head with `gis.layer.publish` capability.

**Layer editing:** `gis.layer.edit` capability, scoped to department by default. Cross-department edits require explicit grant or elevated role.

**Export:** GIS data export (`gis.layer.export`) is a separately controlled capability due to the sensitivity of spatial data about infrastructure and hazard zones.

---

### 10.7 Analytics and Reporting

The access dimensions that matter in Analytics are: report scope, data classification, and publication state.

**Data access:** Analytics queries are scoped to the user's authority scope. An analyst can query incident data for their department. A Deputy Chairman can query data for all departments in their authority scope. Organization-wide statistics are available to senior leadership and designated analytical roles.

**Report creation:** Users with `analytics.report.create` can create reports. The report's data scope is bounded by the creator's authority scope at creation time — they cannot create reports containing data they cannot individually access.

**Report publication:** Reports can be published to organization-wide visibility by users with `analytics.report.publish`. Published reports are accessible to any user with `analytics.report.view` and the appropriate clearance for the report's classification.

**Raw data access:** Accessing underlying incident records (not aggregated statistics) requires separate, more restrictive capability: `analytics.data.view.raw`. This is granted only to senior analysts and above.

---

### 10.8 Administration Panel

The access dimensions that matter in Administration are entirely governed by the administrative SoD model from Section 9. Each administrative function is available only to the specific administrative role designated for it.

**User management panel:** `user_admin` only
**Role management panel:** `role_admin` only, read access for `security_admin`
**Org structure panel:** `org_admin` only
**Security settings panel:** `security_admin` only
**System configuration panel:** `platform_admin` only
**Delegation management:** delegators themselves + `org_admin` for oversight

No single administrative role grants access to more than one panel category.

---

### 10.9 Audit and Logs

The access dimensions that matter in Audit are: log scope and log sensitivity.

**Operational audit log:** Actions taken by users on business records. Accessible by `audit_viewer` role, scoped to the viewer's organizational authority — a department-level auditor can see audit records for their department's resources; a platform-level auditor can see all records.

**Security audit log:** Authentication events, authorization denials, role changes, classification changes. Accessible by `security_admin` and designated `security_audit_viewer` roles only.

**Administrative audit log:** Configuration changes, user creation, role assignments. Accessible by `security_admin` and `audit_viewer` (read-only). The `platform_admin` can view their own audit records but not delete or modify them.

No user can view or modify the audit records of their own privileged actions in a way that would allow self-concealment.

---

## 11. Confidentiality and Information Classification Model

### 11.1 Classification Levels

The platform defines five classification levels in ascending order of sensitivity:

**Level 0 — Unrestricted (Internal)**
Information that can be shared with any authenticated platform user. Organizational announcements, general procedures, public-facing regulatory documents stored internally for reference. No clearance requirement beyond platform membership.

**Level 1 — Internal**
Information intended for internal use within the organization but not requiring special handling. Most routine correspondence, standard operating procedures, routine task records. All platform users with a current active position have Level 1 clearance by default.

**Level 2 — Department-Confidential**
Information restricted to a specific department and its command chain. Departmental operational documents, internal assessments, preliminary analytical reports. Access is bounded by department scope and reporting chain. Positions at department head level and above within the scope have Level 2 clearance.

**Level 3 — Restricted**
Information restricted to defined senior positions and above. Sensitive operational assessments, emergency preparedness details that should not be broadly circulated. Requires explicit Level 3 clearance assignment by the `security_admin`. Typically granted to Deputy Chairman level and above, plus specifically designated analyst positions.

**Level 4 — Confidential**
Sensitive information requiring strict access control. Civil defense operational data, sensitive incident assessments with security implications, personnel security matters. Access restricted to a small defined set of positions. Explicitly assigned by `security_admin` with documented justification.

**Level 5 — Secret**
The highest classification level in the platform. Reserved for matters of significant national importance within the platform's operational scope. Accessible only to Chairman, designated Deputy Chairmen, and positions explicitly cleared by the `security_admin`. Emergency operational plans may fall in this category.

---

### 11.2 Classification Assignment

**Who can classify:** Any user who creates a resource classifies it at the time of creation. They may set the classification at or below their own clearance level — a user with Level 2 clearance cannot create a Level 3 document.

**Who can reclassify upward:** Any user with the appropriate target clearance level and `[resource].classify.elevate` capability. Reclassification is audit-logged.

**Who can reclassify downward (declassify):** Only users with `[resource].classify.reduce` capability — typically `security_admin` or a designated senior authority. Declassification is a significant event, requires a justification record, and is prominently audit-logged.

**Default classification:** If a user creates a resource and does not specify a classification, the platform applies a default based on the resource type and the creating department's standard classification profile. A department handling Level 3 materials by default produces Level 3 resources unless explicitly set lower.

---

### 11.3 Classification in Workflow

Workflows (approval chains, task assignments) respect classification at every step. The system verifies that each participant in a workflow has the clearance level required for the document or task being routed to them. If a required approver's position does not have sufficient clearance for the resource being approved, this is a configuration error that is surfaced to the `org_admin` — not silently bypassed.

---

### 11.4 Classification and Search

Search results are filtered by the requesting user's clearance level. A user searching for "flood incident" receives only results at classifications ≤ their clearance. The existence of higher-classified records matching their query is not revealed. Search result counts that could allow inference of classified content are suppressed.

---

## 12. Auditability and Access Governance Model

### 12.1 What Must Be Logged

The following events produce immutable audit records. This list is comprehensive and non-negotiable:

**Identity and Authentication:**
- Successful login (with method, IP address, session ID)
- Failed login attempt (with IP address)
- Password change or reset
- Session termination (voluntary or forced)
- MFA enrollment or change

**Authorization:**
- Access denial for any resource at Level 2 or above
- Access denial for administrative functions
- Emergency access grant used
- Any attempt to access a resource above the user's clearance level

**Role and Permission Management:**
- Role assigned to a user
- Role removed from a user
- Role definition changed (permissions added or removed)
- Positional role assignment changed
- SoD rule violation detected or overridden

**Organizational Changes:**
- Department created, modified, or deactivated
- Position created, modified, or deactivated
- Position occupancy assigned or ended
- Reporting line changed
- Delegation created, modified, expired, or revoked

**Document Lifecycle:**
- Document created
- Document classification set or changed
- Document submitted for approval
- Approval action taken (approved, rejected, returned) — including acting/delegated approvals
- Document signed or published
- Document archived

**Task Lifecycle:**
- Task created and assigned
- Task reassigned
- Task status changed to complete
- Overdue task escalated

**File Management:**
- File uploaded
- File downloaded (for Level 2+ classified files)
- File classification changed
- File deleted

**Administrative Actions:**
- User account created, modified, suspended, reactivated, deleted
- Security configuration changed
- Clearance level assigned or modified
- Audit retention policy changed
- System configuration changed

---

### 12.2 Audit Record Structure

Every audit record contains at minimum:
- **Event ID:** globally unique, monotonically increasing
- **Timestamp:** UTC, millisecond precision, server-generated (not client-reported)
- **User ID:** the acting user
- **Session ID:** links to the authenticated session
- **Effective position:** the position under which the action was taken (relevant for delegation and acting scenarios)
- **Delegation reference:** if the action was taken under a delegation, the delegation record ID
- **Action type:** standardized event type from a defined taxonomy
- **Resource type:** the type of resource acted upon
- **Resource ID:** the specific resource
- **Result:** success or failure
- **Failure reason:** if failure, the authorization layer and reason code
- **IP address:** originating network address
- **Hash chain value:** hash of (previous record hash + current record content), enabling tamper detection

---

### 12.3 Access Decision Explainability

For any significant access decision (particularly denials), the system must be able to produce a human-readable explanation:

*"Access denied for User [A] to Document [D]. Reason: The document is classified at Level 3 (Restricted). User [A]'s effective clearance level is 2 (Department-Confidential) based on their current position [P]. No active delegation or acting assignment grants elevated clearance."*

This explainability requirement means the authorization evaluation must preserve the reasoning chain, not just produce a boolean. The reasoning chain is stored alongside the audit record for security-significant decisions.

---

### 12.4 Governance Processes

**Periodic access review:** Every 90 days, a report is generated listing all users with non-standard functional role assignments, all active delegations, and all users with Level 3+ clearance. The `security_admin` must review and certify or revoke each item.

**Orphan assignment detection:** When a user's position occupancy ends, a check is run for functional role assignments that are no longer appropriate given the new position. The `user_admin` is alerted to review and remove orphaned role assignments.

**Delegation expiry monitoring:** Delegations approaching their expiry date generate a notification to the delegator. Delegations that expire with in-progress workflows generate an alert to the relevant `org_admin`.

---

## 13. SSO and Identity Governance Readiness

### 13.1 Architectural Principle

The IAM domain is built as an authentication abstraction layer. The internal platform token is always a platform-issued JWT — but the mechanism that validates the user's identity before issuing that token is pluggable. This means SSO integration does not require rebuilding the authorization model.

**Phase 1 (current):** The IAM domain validates username/password against its own credential store and issues a platform JWT.

**Phase 2 (LDAP/AD):** The IAM domain delegates credential validation to an organization LDAP directory. Successful LDAP bind → IAM issues platform JWT. The platform JWT claims remain unchanged.

**Phase 3 (SAML/OIDC):** The IAM domain acts as a SAML Service Provider or OIDC Relying Party. A government identity provider authenticates the user. The IAM domain receives the SAML assertion or OIDC ID token, maps the external identity to a platform user record, and issues a platform JWT. The rest of the platform is unchanged.

---

### 13.2 Identity Mapping

When an external identity provider is integrated, the IAM domain maintains an identity mapping table: external identity (IDP user ID or email) → internal platform user ID. This mapping:
- Is created when a user first authenticates via SSO (if JIT provisioning is enabled) or pre-provisioned by the `user_admin`
- Is a one-to-one mapping (one external identity per platform user)
- Preserves the internal user ID as the authoritative identifier — all audit records, role assignments, and position occupancies reference the internal ID, not the external identity

This design means that if the organization changes its identity provider (e.g., migrating from LDAP to a new government SSO system), the mapping table is updated without touching the authorization model or audit records.

---

### 13.3 MFA Readiness

The authentication flow is designed to support MFA as an additional factor without architectural changes:

- After primary credential validation, the IAM domain can invoke an MFA verification step before issuing the platform token
- MFA methods (TOTP, SMS OTP) are abstracted behind an MFA provider interface
- For classified operations (Level 3+), the platform can require re-authentication with MFA even if the session was established without it — a "step-up authentication" pattern

MFA configuration is managed by the `security_admin` and can be enforced per role (e.g., all administrative roles require MFA) or per clearance level (Level 3+ clearance users must use MFA).

---

### 13.4 Claims and Attribute Federation

When using external identity providers that supply user attributes (e.g., department codes, position identifiers from a government HR system), the IAM domain can map these attributes to platform concepts:

- An external department code → mapped to the internal department record
- An external position identifier → mapped to the platform position record, triggering automatic occupancy assignment

This claim mapping is configured by the `org_admin` and `security_admin` and enables automated provisioning in organizations with mature HR systems. Unmapped claims are logged and surfaced for review — they do not trigger automatic access grants.

## 14. Key Risks and Design Trade-offs

### Risk 1: Organizational hierarchy diverges from recorded hierarchy

**Risk:** The real-world organization restructures informally (people start reporting to different supervisors, departments absorb responsibilities informally) without the platform hierarchy being updated. The access model then reflects an outdated structure, producing incorrect scope calculations and potentially allowing or denying access incorrectly.

**Mitigation:** Organizational structure changes are governed administrative operations. The `org_admin` must update the platform hierarchy to reflect real changes. A periodic review (quarterly at minimum) compares recorded hierarchy against HR records. Platform access decisions that seem anomalous (e.g., a user being denied access to their own department's documents) should trigger a hierarchy consistency check as a first diagnostic step.

---

### Risk 2: Role proliferation eroding the model's clarity

**Risk:** Over time, administrators create increasingly specific roles to handle edge cases — "Deputy Head of Department X during emergencies with Level 3 clearance who also coordinates with the analytical unit." This produces hundreds of roles, no one understands the full model, and security reviews become impossible.

**Mitigation:** Role creation must be a governed process requiring justification and `security_admin` approval. The general-purpose answer to edge cases should be: functional roles (scoped additions to a position's base capability) and delegations (time-bounded grants). New roles are a last resort. The role audit review every 90 days identifies roles with zero or one assigned user — these are candidates for removal.

---

### Risk 3: Delegation chains creating unintended authority expansion

**Risk:** A user delegates authority to User B, who interprets that delegation broadly, effectively acquiring more access than the delegator intended.

**Mitigation:** Delegation records specify authority type precisely, not broadly. "Approval authority for incoming correspondence" is a delegation. "All my permissions" is never a valid delegation type. The delegation record's authority_type field maps to a bounded enumeration of delegation types defined at platform design time — free-text delegations are not supported.

---

### Risk 4: The acting assignment model creating shadow authority

**Risk:** A user is placed in an acting assignment long after the original position holder has returned, and the acting status is never formally closed. The user retains expanded authority they should no longer have.

**Mitigation:** Acting assignments have mandatory end dates. The platform enforces expiry automatically. Any acting assignment approaching expiry sends a notification to the `org_admin`. Expired acting assignments are automatically closed — no manual action required to revoke access.

---

### Risk 5: Classification becoming meaningless through overuse

**Risk:** Administrators classify routine documents at high levels "just in case," resulting in so much material at high classification that users with lower clearance cannot access materials needed for their work, leading to pressure to lower clearances broadly or grant blanket exceptions.

**Mitigation:** Default classification rules are set conservatively but appropriately — not defensively high. Classification training for document creators. Classification audit: a periodic review of documents classified at Level 3+ that have not been accessed in 90+ days. These may be over-classified.

---

### Trade-off: Computed scope vs. explicit ACLs

The model uses hierarchical scope computation (derived from the org chart) as the primary access mechanism rather than per-resource ACLs for every record. This is correct for a government hierarchy — it means access is predictable and does not require manual management of thousands of individual resource permissions.

The trade-off is that scope computation requires maintaining an accurate organizational hierarchy. An outdated hierarchy produces incorrect scope calculations. The mitigation is the governance processes described above.

For the minority of resources that need access patterns outside the natural scope (explicit cross-department sharing, specific user grants), explicit grant records supplement the computed scope. These are the exception, not the norm.

---

### Trade-off: Workflow-position binding vs. flexibility

Binding document approvals and task assignments to positions (not users) is organizationally correct but operationally rigid. A vacancy in a critical approval position halts workflows.

The trade-off is accepted because the alternative — routing to users rather than positions — makes workflows fragile to personnel changes and violates the organizational authority model. The mitigation is a clear vacancy escalation rule: vacant positions escalate to the reporting-to position. This means vacancies never halt workflows indefinitely — they always have a fallback.

---

## 15. Final Recommended Access Governance Architecture

The CoESCD platform's access governance is built on four inseparable pillars:

---

**Pillar 1 — The Organizational Model as the Authority Foundation**

Every access decision is ultimately grounded in the organizational hierarchy. Positions are the unit of authority. Users exercise authority because they occupy positions. Workflows route to positions. The organizational model is the source of truth for scope computation, command chain validation, and approval chain resolution. Maintaining this model accurately is an organizational responsibility, not just a technical one. The platform must make organizational changes easy to execute and impossible to forget — every structural change triggers downstream reviews.

---

**Pillar 2 — The Four-Layer Authorization Engine as the Single Decision Point**

All access decisions — across all modules, for all resource types, for all user types — flow through the four-layer evaluation engine: capability → scope → classification → policy. No module evaluates access independently. No shortcut exists. This consistency is what makes the model auditable and explainable. It also means that fixing a security issue in the authorization model fixes it everywhere simultaneously.

---

**Pillar 3 — Delegation and Temporary Authority as First-Class Features**

Delegation is not an afterthought. It is a formally governed feature with its own data model, its own audit trail, and its own governance processes. The ability to delegate safely is what makes the organizational model operationally viable in a real government institution where people go on leave, change roles, and handle situations that require cross-position collaboration. Delegation that is well-governed enables flexibility without sacrificing accountability.

---

**Pillar 4 — Audit as the Verification Backbone**

The authorization model is only trustworthy if it is verifiable. Every significant decision — grant, deny, delegation, override, administrative change — produces an immutable, explainable, hash-chained audit record. The audit system is not optional and is not built as an afterthought in a later phase. It is part of the platform from the first feature deployed. Without a complete audit trail from day one, historical access analysis is impossible and the organization cannot demonstrate compliance with its own governance obligations.

---

These four pillars are implemented in two platform domains — the IAM domain (Pillar 1 inputs, Pillar 4 infrastructure) and the Authorization domain (Pillars 1 through 4 at decision time) — with cross-cutting infrastructure support from the Audit domain. No other domain owns any piece of this model. The discipline of keeping access governance in its designated domains is what makes this architecture maintainable over the multi-decade lifetime of a government institutional platform.
